# Audit 0010: External integration boundaries failure modes and site performance

## Scope

Examined, at branch `codebase-cleanup`, commit `57996be`, 2026-09-21:

- **Half 1 - integration boundaries.** Every entry point named in the brief, traced end to end: Google Docs (`src/textbook-loader/gdocsdk.ts`, consumed via `loader.ts`), Cloudflare R2 (`src/textbook-loader/renderers/audio/r2-cache.ts` and its three callers), ElevenLabs (`elevenlabs-tts.ts`, orchestrated by `renderers/audio/renderer.ts`), Gemini (`equation-describer.ts`, and `gemini-tts.ts` as dormant code), Algolia (`algolia.ts`, called from `src/content.config.ts:100`), and the pinned CDN hostnames in `src/data/chapter-timing.ts` (71 URLs). Configuration via `astro.config.mjs` env schema, `src/lib/build-mode.ts`, and `src/content.config.ts`. Build/deploy behaviour via `.github/workflows/{deploy,test}.yml`.
- **Half 2 - performance.** The section-page reader journey: `Reader.astro` and the section route `src/pages/chapters/[version]/[chapter]/[section].astro`, the client JS entering via `src/lib/{reader,word-highlight,word-align,follow-scroll,audio-player,audio-source-switch}.ts`, the committed `.words.json` timing payloads (`public/audio/ch*/*.words.json`), the image pipeline (`src/components/nodes/Figure.astro`, `astro.config.mjs` image service), fonts (`src/components/BaseHead.astro`, `src/fonts/`), third-party runtime (Plausible, Microsoft Clarity, DocSearch, OWID iframes), and build-time drivers reasoned from code (Typst PDF renderer, image processing, Google Docs fetch, audio pipeline, Algolia indexing).

Also examined because the trace led there, though outside the brief's table: the `@foreview/ais-logos-astro` logos loader (`src/content.config.ts:20-28`) and `src/lib/og.ts` (og-image service).

**Explicitly not examined:** translation/edition multiplexing beyond what the trace touched (audit 0007/0008 scope), the transformer/AST internals (audit 0008), audio content quality (audit C), `scripts/` retirement (task:0010, decided), and any correctness testing of the live deployed site - no HTTP requests were made to production endpoints.

## Method

**Constraint honoured: no build.** `pnpm build`, `verify`, `typecheck`, `test:smoke`, and `test:a11y` were not run (VM memory constraint, per SHARED.md hard constraint 2). All conclusions below come from (a) reading source with `file:line` anchors, and (b) byte-level measurement of files already on disk. No git state was changed; the working tree was already modified by another party (`src/pages/teach.astro` was dirty on arrival and was left untouched).

1. **Integration trace.** For each service, read its entry-point module in full, then read its callers (`rg` for the exported symbols) until the failure path reached either a build step or a rendered page artifact. Every finding cites the line(s) that establish the behaviour.
2. **Byte measurement.** All numbers measured on this working copy with `stat`/`du`/`gzip -c`/`zstd`:
   - `find public/audio -name '*.words.json' -printf '%s\n'` - 71 files, raw byte sizes summed, min/max/median computed with awk.
   - Aggregate compressed size as a transfer-encoding proxy: `find public/audio -name '*.words.json' -print0 | xargs -0 gzip -c | wc -c` and the same with `zstd -19 -c`.
   - Repo weight: `git ls-files src/assets | xargs du -b` (57 files, 16.8 MB) and working-tree `du -sb` for the gitignored `src/assets/uc/` (344 files, 201.7 MB) and `.cache/docs/` (8.7 MB, committed).
   - Font payload: file sizes of the latin woff2 files inside `node_modules/@fontsource*` (12,756 B Righteous latin-400; 26,576 B Jost latin variable).
3. **Build-mode characterisation.** `src/lib/build-mode.ts` plus `content.config.ts` and `deploy.yml` determine what a contributor build, the CI deploy build, and a full maintainer build each fetch, render, and upload; findings 7's numbers come from these three files read together.
4. **Cross-checks against prior audits.** Audit 0006 F3 (env var split-brain) and 0004 F2 (committed image weight) were read first; findings here either build on them or avoid repeating them.

Selection limits: the audio renderer's interaction with the external `atlas-podcast` repo (`pipeline.py --check-remote`) is cited only from comments in this repo; that repo was not read. R2, ElevenLabs, Gemini, and Algolia were not exercised live.

## Findings

### F1 - The eager `.words.json` fetch is the largest measurable reader-facing cost this repo introduces per timed page

**Observation.** The repo commits 71 word-timing payloads under `public/audio/ch*/`, served verbatim by the CDN/web host (they are in `public/`, so no build processing touches them). Measured on this working copy: **total 6,084,574 bytes raw** (6.08 MB; mean 85,698 B, median 77,244 B, range 4,809–319,453 B). As a transfer-size proxy, the same 71 files gzip to **1,561,279 bytes** and zstd-19 to 1,346,131 bytes - i.e. roughly **22 KB average on the wire if the host compresses JSON**, 86 KB if it does not. The fetch is **eager**: `src/lib/word-highlight.ts:598-607` reads `data-words-url` from the page (`src/pages/chapters/[version]/[chapter]/[section].astro:377-391`) and calls `fetch(wordsUrl)` during `initWordHighlight()`, unconditionally, on every section page that has timings - there is no gate on playback intent. By contrast the audio itself is properly lazy: `<audio id="audio-element" preload="none">` (`Reader.astro:376`) and the inline player never downloads audio bytes until the reader presses play.

**Inference.** On a timed section page, the read-along coordinates are downloaded for every visitor whether or not they ever listen - likely the single largest *eager* transfer after the document itself (HTML+CSS+JS are unmeasured here; see Limitations). The irony is structural: the audio is deferred but its index is not. This is also the cheapest large win in this audit - gating the fetch on first play intent is a small client-side change requiring no pipeline change. The committed-table design itself (71 files, 6 MB of repo per content refresh) is acceptable repo weight, but it grows linearly with sections × languages if the pipeline keeps committing one JSON per section (relevant to the 2 editions × 5 languages scaling axis).

### F2 - Every R2 failure path is warn-and-continue, so a degraded R2 produces a "successful" build that ships 404 links

**Observation.** In `r2-cache.ts`, **no function throws on failure**. Download paths catch errors and `console.warn` (`r2-cache.ts:80-84`, and again for final audio at `r2-cache.ts:141-146`); upload paths do the same (`:110-117`, `:160-167`, `:196-203`). `NoSuchKey` is swallowed as expected (`:77-79`, `:140-142`). The docstring of `pullFinalAudioBatch` says it outright: *"Silently skips files that don't exist in R2"* (`r2-cache.ts:131-133`). The consequences reach the shipped site because the caller sets CDN links **before** knowing the upload succeeded: the audio renderer assigns `section.audioLink = ${CDN_BASE}/audio/${filename}` in Phase 2 (`renderers/audio/renderer.ts:100`) and the PDF renderer returns `${CDN_BASE}/pdf/${pdfFilename}` unconditionally (`renderers/pdf/renderer.ts:67, 96`) - then `pushPublicFiles` may fail silently (`r2-cache.ts:160-203`). If R2 is unreachable, the wrong bucket is configured, or a put fails mid-batch, the build exits 0, deploys, and the live page renders "Listen"/"Download PDF" links whose targets 404. The upload-side list-then-filter (`:88-100`, `:174-187`) also degrades silently: a failed `ListObjectsV2Command` means every local file is treated as new and re-uploaded (harmless), but a failed *get* during pull means the build continues without the audio it believed it had.

**Inference.** This is the brief's "quietly wrong site" class, and it directly contradicts PRINCIPLES.md §2 ("Fail loud, not silent") - honoured elsewhere (see F9) but not in this module. The blast radius is unusually bad because the failure is *invisible at build time and wrong at read time*: no maintainer sees an error, no CI log shows a warning beyond one `console.warn` line among many, and the deployed site loses audio/PDF links without any signal that ties the loss to R2. Note the contrast inside the same file: `pullFromR2` for chunk caches *should* stay soft (cache misses are legitimately expected and fall back to synthesis), but `pushPublicFiles` and the final-audio push are **delivery-critical** and should not be.

### F3 - Read-along audio and word timings pair by two different schemes, so a narration edit can silently desynchronise the highlight

**Observation.** The audio URL is **content-hashed** on the section's narration text (`renderer.ts:93-99`, sha256 of the rendered paragraphs; the file name embeds the hash) and the live build prefers its own fresh link (`section-audio.ts:86-88`, `publishedAudioUrl ?? timing?.publishedUrl`). The word timings are **position-pinned**: `wordsUrl` is always the static `/audio/chX-sY.words.json` (`chapter-timing.ts`, every entry), never hashed on content. The committed `.words.json` files were measured against the recording at `publishedUrl` - the table's header comment says a TTS re-render "invalidates the whole file at once" and that `pipeline.py --check-remote` in `atlas-podcast` reports when the published audio has moved (`chapter-timing.ts:1-16`). There is **no build-time validation** linking `wordsUrl` to the audio file it pairs with: `section-audio.ts:80-88` resolves the two URLs independently, and `word-highlight.ts:607` fetches whatever URL it is given.

**Inference.** The failure chain: a writer edits a section → maintainer build re-renders TTS → new content hash → R2 gains a new `final-audio/...mp3` → next deploy build's `section.audioLink` points at the new file → the committed `.words.json` (still keyed by chapter/section position) now describes the *old* recording. If timings were not regenerated in the same operation, every word highlight on that section drifts by the length of the edit - a quietly wrong read-along with zero build errors. The design acknowledges the coupling in prose (`chapter-timing.ts:4-16`, `section-audio.ts:1-24`) and assigns detection to an external repo's script, but nothing in this repo enforces the invariant. The smallest structural fix is to stamp each `.words.json` with the content hash it was measured against and have the build (or the client) refuse/refetch on mismatch. Note this is exactly the kind of coupling that multiplies with Edition 2 × languages: each edition/language needs its own timing set and the position-pinned table gives both no room to be validated independently.

### F4 - Algolia indexing is delete-then-save with no retry, inside the content collection load: a partial failure empties the live search index

**Observation.** `indexTextbook` first runs `client.deleteBy({ filters: 'version:${v}' })` (`algolia.ts:139-145`), then `saveObjects` (`:147-152`). Neither call is retried or wrapped; the only error handling is absence of any. The caller is the Astro content collection loader itself (`content.config.ts:97-107`), gated to maintainer builds (`mode.indexAlgolia = hasGoogleCreds && hasAlgoliaWrite`, `build-mode.ts:47`). If `saveObjects` fails after `deleteBy` succeeded - network blip, key rotation, Algolia outage - the previous records for that version are already gone, and the thrown error propagates out of the collection loader, failing the build. Audit 0007 already flagged the deleteBy-wipe shape itself; the addition here is the **failure-ordering**: on save failure, the build fails *and* the production index for that version is now empty, so search stays broken on the live site until the next successful maintainer build. Nothing in the deploy pipeline (`.github/workflows/deploy.yml`) rolls the index back.

**Inference.** The asymmetric failure means one bad deploy leaves the site live but search silent - a degraded reading experience indistinguishable from "no results found" to users, and invisible unless someone searches. The standard mitigations are cheap: save first (batch upserts are idempotent by `objectID`), delete stale records *after* the save succeeds; or stage into a temp index and swap. This matters more as content grows: 2 editions × 5 languages multiplies the records per build and the failure surface per deploy.

### F5 - Four configuration inputs bypass the typed env schema, including voice/model IDs whose silent defaults decide what narration sounds like

**Observation.** `astro.config.mjs` declares 13 env vars in its typed `env.schema`; at least four are additionally read raw from `process.env` outside it: `ELEVENLABS_VOICE_ID` and `ELEVENLABS_MODEL_ID` (`elevenlabs-tts.ts:9-10`), `GEMINI_TTS_MODEL` (`gemini-tts.ts:9`, dormant), and `SKIP_AUDIO_DOWNLOAD` (`renderer.ts:53`). The voice and model carry **hardcoded defaults** (`'JBFqnCBsd6RMkjVDRZzb'` = "George", `'eleven_turbo_v2_5'`) at module load time. `BuildMode` (`build-mode.ts`) neither sees nor reports these. Audit 0006 F3 established the env split-brain; what it means operationally: a maintainer build with only `ELEVENLABS_API_KEY` set silently narrates with the default voice and model; a typo'd variable name (`ELEVENLABS_VOICEID`) silently does the same; and neither mistake is visible in the BuildMode summary that prints at build start (`content.config.ts:76`, `build-mode.ts:64-69`).

**Inference.** The risk is specific and live: the owner's stated intent is to change the ElevenLabs speaker and possibly the model, and task:0001–0006 are about reducing dependence on a freelancer's accounts. Under the current setup, "which voice produced the published audio" is not recorded anywhere in this repo's build surface - it is whatever env vars happened to be set (or not) in the shell that ran the TTS render. A voice switch could therefore produce one chapter in the new voice and others in the old, with no loud failure - the narration changes, the content hash changes, new audio files appear, and nothing in the pipeline compares. Folding these four into the typed schema (or at least echoing effective values in the BuildMode summary) converts a silent variance into a visible one.

### F6 - A sixth external integration not in the brief's table: the logos loader hard-fails the build on its index and silently drops individual logos

**Observation.** `content.config.ts:20-28` wires `logosLoader` from `@foreview/ais-logos-astro` against four org URLs (cesia.org, ml4good.org, bluedot.org, enais.co). The loader (reading `node_modules/@foreview/ais-logos-astro/dist/loader.js`, `:66-155`) fetches an index from a **third-party GitHub Pages site** (`https://foreview.github.io/aisafety-logos/index.json`, `loader.js:4-5`) on every build; if that fetch fails the loader throws and the build fails (`loader.js:76-79`). Individual logo downloads, however, degrade silently: `downloadFile` returns `false` on any error (`loader.js:17-30`), the loader logs a `logger.warn` and stores the variant with `color: undefined` (`loader.js:120-131`) - the shipped page just lacks the logo. The `logos/` output lands in `public/logos/` (`loader.js:73`), i.e. it is **not committed or cached**, so every build re-downloads from third-party uptime.

**Inference.** Two failure modes in one integration: an outage of someone else's GitHub Pages repo breaks this repo's deploy (loud but obscure - the error will name a logos index, not a content source), while a partial outage silently shaves logos off the page. Given the project's cache-the-externals pattern for Google Docs (`.cache/docs/` is committed precisely so contributors and CI survive upstream changes), the logos index has no equivalent treatment. Small blast radius today (four orgs), but it is the same shape that bit harder elsewhere in this audit.

### F7 - Build-time cost is dominated by what each build mode re-derives, and the deploy build re-renders all PDFs and re-processes 200 MB of images on every push

**Observation.** Three build profiles fall out of `build-mode.ts` + `content.config.ts` + `loader.ts:74-83`:

- **Contributor** (no credentials): cache-only Google Docs from the committed 8.7 MB `.cache/docs/` snapshot; `skipPdf` and `skipAudio` auto-on (`build-mode.ts:36-37`); no Algolia write; no R2 traffic. Its gap: `src/assets/uc/` (344 files, 201.7 MB working tree) is **gitignored**, so a contributor clone has cached docs but none of the doc images - `gdocsdk.ts:33-40` deliberately keeps the cache hit and `Figure.astro:31-34` shows the placeholder only in dev; a contributor's prerendered *production-style* build silently ships caption-only figures (the code comment calls this "by design" - flagged here so the owner can confirm it still is).
- **Deploy (GitHub Actions, `deploy.yml:36-51`)**: full secrets, `SKIP_AUDIO="1"` - but `SKIP_PDF` is not set, so `loader.ts:77-79` runs the **Typst renderer for all 8 chapters on every push** (`renderChapter` compiles via `execSync` unless the content-hash-keyed file already exists locally, `pdf/renderer.ts:56-59`, and CI has no cache for `.cache/uc`). The audio renderer still runs in skip-generation mode: it pulls final audio from R2 (Phase 3), falls back to stale stable-key files (Phase 4, commented "serves stale audio", `renderer.ts:113-125`), and `pushToR2`/`pushPublicFiles` re-list and re-push the public audio each build.
- **Full maintainer**: everything above plus Google Docs fetches (one `documents.get` per chapter, sequential - `gdocsdk.ts:47`, looped at `loader.ts:34-37`), image downloads (p-limit 5, `gdocsdk.ts:143-146`), ElevenLabs synthesis (p-throttle 80 RPM, `elevenlabs-tts.ts:12-16`), two-pass ffmpeg loudness normalization per section (`elevenlabs-tts.ts:289-336`), and Algolia indexing.

On top of both deploy and maintainer builds, Astro's sharp image service processes every image the pages reference - `Figure.astro:14` globs all 344 files in `src/assets/uc/*` (201.7 MB) and `index.astro:12-15` imports several ~0.7–1.2 MB originals - with no build cache between CI runs.

**Inference.** The contributor/deploys split is coherent and the hash-keyed artifacts (PDF, audio) are well designed for idempotency - but the deploy profile re-pays three large costs on every push that have nothing to do with what changed: Typst compilation of unchanged chapters (hash-keyed but cache-less in CI), sharp processing of a 200 MB gitignored image set, and R2 list/push round-trips. As Edition 2 and translations land (chapters roughly double), deploy wall-time grows linearly in the most expensive hops first. A CI cache for `.cache/uc` and the Typst outputs is the smallest structural unblock; the deeper question (whether deploy should render PDFs at all vs. publish them from a maintainer run) is an owner decision.

### F8 - Client-side third-party runtime: two analytics stacks load on every page and DocSearch loads unconditionally, but none block render; OWID iframes degrade to an infinite spinner

**Observation.** Every page ships: Plausible (`<script async src="https://plausible.io/js/...">` + inline init, `Reader.astro:59-63` and `Default.astro:24-28` - `async`, non-blocking); **Microsoft Clarity** (`BaseHead.astro:29-38`, an inline head bootstrap that inserts `clarity.ms/tag/...` with `t.async=1` - the brief's third-party list did not include it); and DocSearch (`DocSearchProvider.astro:12-55`, which injects `@docsearch/css` **and** the ~docsearch UMD bundle from jsdelivr and calls `docsearch(...)` on page load - the trigger button only *opens* the modal, so the full search client is paid by every reader regardless of intent). Chapter figures embed third-party iframes (`Iframe.astro:32-38`, `loading="lazy"`) whose failure state is a spinner that never resolves (`Iframe.astro:22-28` renders a `role="status"` spinner inside the 600px frame with no timeout or error message). Client JS authored in-repo totals ~2,150 lines across `audio-player` (484) + `word-highlight` (724) + `word-align` (327) + `reader` (256) + `follow-scroll` (90) + `audio-source-switch` (110) + `sentences` (53), plus component scripts - Astro bundles and minifies these per page; the served byte count was not measured (see Limitations).

**Inference.** The heaviest reader costs here are (a) the DocSearch bundle+CSS fetched on every page for a modal most readers never open - deferring to first trigger interaction is a known, small pattern and the trigger already exists - and (b) two analytics beacons where the site's own README-adjacent docs imply a privacy-friendly posture; Clarity at least is async. None of the three is render-blocking, so the practical effect is bandwidth and third-party privacy surface rather than LCP. The OWID spinner is the runtime face of the same "third party fails, reader sees nothing" pattern as F2/F6 - with the replacement effort already on the roadmap, the smallest interim fix is a load-timeout that swaps in the caption or a link to the source chart.

### F9 - Google Docs is the one integration that honours §2: it fails loud, retries transient failures, and refuses to poison its cache - use it as the standard

**Observation.** `gdocsdk.ts` handles the failure modes the other modules do not: a cache miss without credentials throws with an actionable message naming both remediations (`:63-73`); image downloads retry HTTP 5xx three times with exponential backoff and treat 4xx as terminal (`:108-129`); after any image failure the module **throws before the partial result is cached**, with the comment explaining the historical silent cache-poisoning it prevents (`:186-196`); and a maintainer build with a stale cache that references missing images re-fetches rather than shipping broken figures (`:31-38`). Its concurrency is bounded (`pLimit(5)`, `:144`). The vendor type (`docs_v1.Schema$DocumentTab`) does leak into `loader.ts`/`Transformer`, so a provider switch would touch several modules - but the pipeline is already isolated behind `Transformer` at the point anything downstream reads.

**Inference.** The codebase contains its own best-practice reference: the failure posture the owner wants (§2) exists and is load-bearing in exactly the integration where a partial failure is hardest to notice. The gap in F2/F4/F6 is therefore not a missing capability but an inconsistent application of a known pattern. When the `bin/atlas` CLI (task:0010) reorganizes service boundaries, making every delivery-critical path meet the `gdocsdk` bar - retry transient errors, throw on partial failure *before* publishing links or wiping state - is the single highest-leverage normalization available, and it can be borrowed almost mechanically from `gdocsdk.ts`.

### F10 - Two TTS provider adapters exist with duplicated ffmpeg post-processing, and the unused one encodes different partial-failure semantics

**Observation.** `gemini-tts.ts` is imported by nothing (its own comment says so and defers the decision to task:0008, `gemini-tts.ts:117-122`), yet it is a complete second provider adapter: its own throttle (10 RPM), cache format (`.pcm`), and ffmpeg normalization - the loudness/seek-correctness comments are duplicated nearly verbatim between `elevenlabs-tts.ts:280-295` and `gemini-tts.ts:128-142`. Their failure semantics diverge: on a failed paragraph, ElevenLabs aborts the *whole section* (`failed > 0 → Buffer.alloc(0)`, `elevenlabs-tts.ts:97-101`) while Gemini **silently concatenates around the gap** (`gemini-tts.ts:97-102`, "Assemble in order, skipping failures") - the same outage would produce a missing section under one adapter and a *narration with a paragraph silently missing* under the other, both changing the content hash that drives audio URLs (F3).

**Inference.** The duplication is deliberate retention (the comment is explicit and reasonable), but the divergent partial-failure semantics are a trap the moment a second provider is actually enabled - and they interact with the timing pipeline: a silently shortened narration still hashes to a *new* hash, so the desynchronisation in F3 would occur with no error anywhere. The cheapest prophylactic is to extract the shared ffmpeg normalization into one module and give both adapters an identical, loud, partial-failure contract before either is next used.

## Limitations

- **No build was executed.** Per the shared brief's hard constraint, nothing that renders the site was run. Consequently: (a) the **served, minified client JS size** per page is unknown - F1's reader-cost claim is precise only for `.words.json`; the TS line counts are inputs, not outputs; (b) sharp's actual output sizes/formats for `Figure.astro` images are inferred - `<Image src={imageModule} alt="" />` (`Figure.astro:30`) passes no explicit `width`/`densities`, so whether readers get downscaled derivatives or merely webp re-encodes at original width is **inference from Astro's documented defaults, not measurement**; (c) deploy wall-time composition (F7) is reasoned, not timed.
- **Transfer encoding was not observed.** The gzip/zstd figures in F1 are compression proxies measured locally; whether the production host actually compresses `application/json` on `atlas.foreviewusercontent.com`-adjacent paths was not verified (no HTTP requests to production were made).
- **Section total vs. timed total.** 71 sections have timings; the total section count could not be established cheaply without a build (a heuristic count of HEADING_1s in `.cache/docs/` yields 105, but the transformer's section-splitting rules were not traced far enough to trust that number). F1's per-page claim is unaffected; a fleet-wide "71 of N pages" ratio should not be quoted from this audit.
- **Behaviour of external services is untested.** R2, ElevenLabs, Gemini, Algolia, and the logos index were not exercised; all F2/F4/F6 failure chains are code-traced causal chains, not reproduced incidents. In particular, whether `client.saveObjects` of `algoliasearch` retries internally was not checked against the SDK version in `pnpm-lock.yaml` - if it does, F4's window narrows to non-retryable errors only.
- **The stale-timings chain in F3 depends on pipeline discipline outside this repo.** `atlas-podcast`'s `pipeline.py --check-remote` was not read; the audit cannot establish how likely the failure is, only that this repo does not enforce the invariant.
- **Method note.** Reading `node_modules/@foreview/ais-logos-astro` dist code (F6) is evidence about the *installed* version, not the package source; a version bump could change its failure modes without this repo noticing.

## Recommendations

Priority order. Sizes: S < 1 session, M 1–2, L multi-session.

1. **Make the delivery-critical R2 paths fail loud (F2).** S. `pushPublicFiles`, `pushFinalAudioFiles`, and the final-audio pull in `r2-cache.ts` should throw (or return a tally the renderers verify) - leaving `pullFromR2` for chunk/eq caches soft, as it is today. What it risks: stricter deploys fail more often until the R2 config is trusted; that is the point. *Safe standalone.*
2. **Gate the `.words.json` fetch on playback intent (F1).** S. In `word-highlight.ts`, defer `fetch(wordsUrl)` until first play/seek intent (or `requestIdleCallback`). What it risks: highlight readiness lags play-start by one round-trip; mitigation is to keep the eager path for preloaded audio pages only. *Safe standalone; largest single reader-facing win measured in this audit.*
3. **Stamp `.words.json` payloads with the narration content hash and verify the pairing (F3).** M. One field in the generator, one check at resolve time (`section-audio.ts`) or fetch time (`word-highlight.ts`); refuses to render a read-along against a mismatched recording instead of silently drifting. ## Disposition
